# أرشيف القصص القديمة: ما أُصلح في الكود وما يبقى مشكلة بيانات

## الخلاصة أولاً

- **لم تُنقل أي قصص قديمة، ولم تُنشأ قصص وهمية.** قاعدة البيانات الجديدة
  (`auqqqwfjxrxizlmeweka`) لا تحتوي قصصاً منتهية، وقاعدة البيانات القديمة **لم تكن
  متاحة من هنا**: لا اتصال ولا بيانات اعتماد لها في هذا المستودع، ولم يُقرأ منها شيء.
- **إصلاح الواجهة لا يعيد بيانات مفقودة.** تعديلات هذه الجولة تجعل الأرشيف يطلب
  صفحاته كلها، ويميّز فشل الجلب من الأرشيف الفارغ، ويسمح بإضافة القصة المنتهية إلى
  مجموعة أبرز القصص. أما ظهور القصص القديمة نفسها فيحتاج **نقل بيانات** من المصدر
  القديم، ولم يُنفَّذ.

## ما أُصلح في الكود

`src/components/ProfileStoryArchiveView.tsx`:

1. **كل الصفحات لا أول 100**: كانت الحلقة تطلب 100 صف وتتوقف عند أول صفحة ناقصة.
   الآن تُكرَّر الصفحات بحد أقصى 50 صفحة (5000 قصة)، مع منع تكرار المعرّف، ومنع
   دخول قصة مستخدم آخر.
2. **لا حلقة بلا نهاية**: صفحة كاملة بلا قصة جديدة تعني أن الخادم لا يحترم
   `p_offset`؛ تتوقف الحلقة بخطأ واضح بدل تعليق الشاشة.
3. **فشل الجلب ليس أرشيفاً فارغاً**: الرسالة تفرّق بين دالة مفقودة (`PGRST202` /
   `42883`)، وجلسة منتهية (`PGRST301` / `401`)، والخطأ الحقيقي، ويبقى زر
   إعادة المحاولة.
4. **إضافة إلى الأبرز**: تبقى كما هي (`aani_add_profile_highlight`) لمجموعة موجودة
   أو مجموعة جديدة، ولا تمسّ `profile_highlights` المحفوظة سابقاً — الإضافة فقط.

الشرط `expires_at <= now()` في `aani_get_my_story_archive` **لم يتغيّر**، ولا
سياسة RLS، ولا مدة 24 ساعة.

## لماذا لا يمكن نقل القصص القديمة من هنا

نقل القصص يحتاج أشياء ليست في هذا المستودع:

1. **مصدر البيانات القديم**: رابط قاعدة البيانات القديمة أو نسخة تصدير (CSV/SQL)
   لجدول `stories` فيها. لا يوجد في `.env` ولا في إعدادات المشروع أي اتصال بها.
2. **تطابق المستخدمين**: `stories.user_id` يشير إلى `profiles(id)`؛ كل معرّف قديم
   يجب أن يقابله صف موجود في `profiles` الجديدة. لا يمكن اختراع هذا التقابل.
3. **وصول ملفات الوسائط**: الروابط القديمة (`media_url` / `thumbnail_url`) قد تكون
   على Supabase Storage القديم أو ImageKit قديم. إن كانت غير قابلة للوصول فلن تظهر
   الصور حتى لو نُقلت الصفوف؛ القرار: نسخ الملفات إلى ImageKit الحالي، أو إبقاء
   الروابط كما هي إن كانت ما تزال تعمل.

بدون (1) لا يوجد ما يُنقل؛ وبدون (2) و(3) لا يصح النقل.

## خطوات النقل (يدوية، لا تُنفَّذ تلقائياً)

1. صدّر من القاعدة القديمة:
   ```sql
   select id, user_id, media_url, media_type, caption, is_close_friends,
          created_at, expires_at, duration_seconds, thumbnail_url,
          filter_key, original_story_id
   from public.stories
   where expires_at <= now();
   ```
2. أنشئ جدول الاستقبال واملأه من التصدير (في جلسة SQL Editor واحدة):
   ```sql
   create table if not exists public.story_archive_import_staging (
     id uuid primary key,
     user_id uuid not null,
     media_url text,
     media_type text not null,
     caption text,
     is_close_friends boolean not null default false,
     created_at timestamptz not null,
     expires_at timestamptz not null,
     duration_seconds integer,
     thumbnail_url text,
     filter_key text,
     original_story_id uuid
   );
   ```
3. شغّل `supabase/APPLY_MANUALLY_story_archive_backfill.sql` (ملف بيانات يدوي،
   ليس ترحيلاً ولا يدخل سلسلة الترحيلات). يتحقق من المستخدمين والأنواع والمدة
   وتاريخ الانتهاء، ثم يُدرج بـ`on conflict (id) do nothing`، ولا يحذف شيئاً.
4. احذف جدول الاستقبال بعد التحقق:
   ```sql
   drop table public.story_archive_import_staging;
   ```
5. تحقّق من الأرشيف على الجهاز نفسه: افتح «أرشيف» في إعدادات الملف الشخصي، ثم
   أضف قصة منتهية إلى مجموعة.

## ما لم يُتحقق منه

- **لا وصول إلى القاعدة القديمة**، فلا تصدير ولا نقل.
- **لا تشغيل فعلي** لسكربت النقل ولا لاستعلاماته.
- **لا اختبار على iPhone Safari** للقص والتكبير في هذه الجولة.
- **لا اختبار لرفع ImageKit ولا لحفظ `profiles.avatar_url`** على جهاز حقيقي.
- لا `db push` ولا أي تغيير مباشر على قاعدة الإنتاج.
